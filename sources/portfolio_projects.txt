The edit river on October 8, 2026. Each dot is one real edit in a row for its wiki, blue for people and orange for bots, drifting left as it ages; rings are new pages.


## Why This Matters

Streaming sketches are usually taught with their error bounds and then trusted. HyperLogLog promises a distinct count within about 1.6% from 4 KB of state. Count-Min promises it never undercounts, and rarely overcounts by more than a small, known share of all events (εN, with probability 1 - δ). Space-Saving promises that every page popular enough to matter (above N/k edits, for k counters) is in its table, with a known error on every count. I wanted to watch those promises hold on real traffic instead of taking them on faith, so this dashboard runs each sketch beside an exact counter on the same events and plots the difference as it happens.



## The Data

Wikimedia publishes every change to every one of its wikis as a server sent events stream. The browser connects to it directly, with no server of mine in between. In my runs it carried 26 to 36 events a second across about 100 wikis, roughly a quarter of them from bots. If the connection drops, the browser reconnects with Last-Event-ID, which carries the stream's Kafka offsets, so it resumes where it stopped; events are deduplicated on their id in case the resume overlaps.



## The Sketches

HyperLogLog hashes each editor name with MurmurHash3, checked against published test vectors and SMHasher's verification value, into 4,096 one byte registers. While there are fewer than about 10,000 distinct editors it estimates from the share of empty registers (linear counting), and above that it switches to the harmonic mean estimator from the original paper. Count-Min counts events per wiki in 4 rows of 1,024 columns with the standard update, so the textbook bound applies as stated. Space-Saving tracks the most edited pages with 200 counters, each carrying its own error term, so every row shows a guaranteed lower bound and an upper bound, with the exact count drawn as a tick between them.



## Measured on Real Data

A node script ran the same sketch code against the live stream for 297 seconds on October 8, 2026: 9,909 events at 33.3 a second. HyperLogLog estimated 986.9 distinct editors against an exact 983, an error of +0.4% against a one sigma bound of 1.6%. Two shorter runs gave -0.3% and -1.2%. Space-Saving showed no violations of its bounds, and Count-Min kept all 12 of the busiest wikis within εN with no undercounts. The run logs are in the repository next to the code.



## Engineering Decisions

Binning by event time. Binning throughput by arrival flagged delivery clumps as bursts: 3 and 2 false bursts in two of the runs, against none when the same rule ran on event time bins. The chart bins by event time and closes a second 2 seconds after the newest event passes it, and the footer still reports what the arrival rule would have flagged.

A rate bug in the feed monitor. The status pill read 23 messages a second while a separate counter saw 33, because events arriving less than a millisecond apart carried almost no weight in the smoothed rate. Pooling arrivals into 50 ms windows fixed it, in the shared code all four dashboards use.

Privacy. Editor names and IP addresses are hashed for counting and never displayed, and titles of user pages are hidden.



## Honest Limitations


  
- Count-Min barely collides here. About 100 wikis in 1,024 columns rarely share a cell, so the bound is shown but hardly stressed. The card says so beside the number.
  
- A short visit exercises only the small range path of HyperLogLog. It switches to the raw estimator at about 10,240 distinct editors, which takes a long session to reach.
  
- Exact counting is affordable at this rate. That is what makes the comparison possible. The sketches earn their keep at volumes where it is not.
  
- The resume path is lightly tested. Wikimedia dropped the stream once during browser testing, and the page reconnected with Last-Event-ID without a duplicate, but no logged run has exercised it.


  

## What This Project Demonstrates

  Three classic streaming algorithms implemented from their papers, tested against their own guarantees, and run on a real public stream in the browser, with their error measured continuously against ground truth.



==================== PROJECT 1: Order Book Microstructure: A Checksum Verified Live Book with Order Flow Analytics
META: Market Microstructure / Live Data / Oct 2026

REPO: "https://github.com/TanayPratapSingh/orderbook-microstructure"
330 second run on BTC/USD (Oct 8 2026): 46,892 of 46,892 book checksums verified, 0 resyncs  |  OFI regression at 1 s: β = 1.10 USD per BTC, R&sup2; = 0.54, n = 300  |  lag p50 89 ms  |  16 tests
The BTC/USD book on October 8, 2026. Darker blue means more bitcoin waiting at that price; the best bid and ask run across it and every trade is a bubble sized by amount.


## Why This Matters

Every trading system starts from a local copy of the order book, built from a snapshot and a stream of deltas, and the classic failure is silent drift. Miss or misapply one update and every number computed from the book is quietly wrong. Kraken publishes a checksum (CRC32) of the top of its book with every update, so drift does not have to be silent. This dashboard rebuilds the book in the browser, verifies it against that checksum on every message, resyncs automatically on a mismatch, and only then computes microstructure statistics from it.



## The Book

The page subscribes to Kraken's public WebSocket at a depth of 100 levels and keeps each side as a sorted array with binary search updates. After each update it truncates both sides back to the subscribed depth, because the exchange stops sending changes for levels that fall out of range. Price and size precision are read from the exchange's instrument channel rather than hardcoded. That matters because the checksum is computed over formatted strings: printing 0.0157 instead of 0.01570000 changes the string and fails every check.



## What It Computes

Order flow imbalance measures whether buyers or sellers are pressing harder at the best prices. Following Cont, Kukanov and Stoikov (2014), each change at the top of the book adds or subtracts size, summed per second, and the page fits a straight line between that and the price change over the same second (ordinary least squares), live, with the slope's standard error. Microprice weights the midpoint by how much size waits on each side. Realized volatility is computed from mid returns at both 1 second and 10 second sampling over the same five minutes, annualized. A liquidity heatmap shows resting size by price over the last four minutes with every trade drawn over it, painted from raw pixel buffers so it keeps up with the feed.



## Measured on Real Data

A node script ran the same book code against the live feed for 330 seconds on October 8, 2026: 47,595 messages, of which 46,891 were book updates, about 142 a second. All 46,892 checksums (the snapshot and every update) matched, with no resyncs. The OFI regression over the last 300 seconds gave a slope of 1.10 USD per BTC of net flow, standard error 0.059, with R&sup2; = 0.54. An earlier 330 second run verified 44,534 of 44,534, and a run switching between BTC, ETH and SOL verified 10,214 of 10,214. To exercise the resync path, a deliberately corrupted update failed its checksum and the book recovered from a fresh snapshot; that case is also in the test suite.



## A Result That Went the Other Way

Microstructure noise usually makes finely sampled realized volatility read higher than coarsely sampled. In both long runs it went the other way: 27.0% annualized at 1 second against 31.9% at 10 seconds in the final run. The 10 second figure rests on only 30 returns, so its sampling error is about 13%, and the page compares the gap with that error instead of always calling it noise. It labels the gap as within sampling error, as noise, or as prices moving in short runs, depending on what the numbers support.



## Honest Limitations


  
- One venue, 100 levels. The book is Kraken's alone, and liquidity beyond the subscribed depth is invisible.
  
- Taker side as reported. Trade direction is the exchange's label, not inferred.
  
- Clock offset in latency. Lag is arrival time minus the exchange timestamp, so it includes any offset between the two clocks.
  
- Background tabs. Browsers throttle timers in hidden tabs, so heatmap columns sampled while the tab is hidden are sparse.
  
- Not investment advice. This is analytics on public market data.


  

## What This Project Demonstrates

  Stateful stream processing with an integrity check on every message and automatic recovery, and quantitative finance statistics computed on top of a book that is known to be correct, all in the browser at more than a hundred messages a second.



==================== PROJECT 2: Live Earthquake Statistics: Gutenberg-Richter, Omori, and a Catalog That Revises Itself
META: Statistical Seismology / Live Data / Oct 2026
BADGE: California b = 0.73 [0.66, 0.85] / 7 catalog revisions caught in 45 min / live USGS polling
TAGS: JavaScript, Statistical Seismology, Maximum Likelihood, Bootstrap, Gutenberg-Richter, Omori-Utsu, Revision Tracking, d3-geo, node:test
REPO: "https://github.com/TanayPratapSingh/live-earthquake-statistics"
1,949 events in the week feed (USGS, Oct 8 2026)  |  California b = 0.73 ± 0.03, bootstrap [0.66, 0.85]  |  45 min of polling: 9 new events, 7 revisions, mean magnitude change 0.19  |  27 tests
The week's earthquakes on October 8, 2026, colored by depth, with rings rippling out from the last hour's events and the latest M 2.5 or larger called out.


## Why This Matters

An earthquake catalog keeps changing after the fact. Automatic solutions get reviewed, magnitudes move, events merge under a new id, and a few are deleted. Every statistic computed from a live feed inherits those changes, so this dashboard does two jobs at once: it computes the classic statistics of seismology from the past week of USGS data, and it keeps a log of everything the catalog revised while the page was open.



## The Statistics

How much rarer is each bigger quake? The Gutenberg-Richter law says the number of earthquakes drops tenfold for every unit of magnitude when the b-value is 1, which is close to what most regions show. The page finds the magnitude above which the catalog is complete (maximum curvature plus the 0.2 correction of Woessner and Wiemer, 2005), estimates b by maximum likelihood (Aki 1965, with Utsu's binning correction), and reports both the Shi and Bolt (1982) uncertainty and a bootstrap interval from 200 resamples that re-estimates the completeness magnitude each time.

How fast do aftershocks fade? For the largest sequence in the window, aftershocks are gathered with Gardner-Knopoff distance and time windows and fitted to the Omori-Utsu law by maximum likelihood (Ogata 1983), with a profile likelihood range on the decay exponent p. With fewer than 30 aftershocks the page draws the sequence without a fit.

Unusual hours. Each hour's count is compared with a Poisson rate from the previous day, and hours with a tail probability below 0.001 are flagged.



## Measured on Real Data

The week feed fetched at 19:09 UTC on October 8, 2026 held 1,949 events, of which 1,905 were earthquakes; the rest were explosions, quarry blasts and ice quakes, which are left out of every statistic. For California, b came out at 0.73 ± 0.03 with a bootstrap interval of [0.66, 0.85] above a completeness magnitude of 0.9, and Alaska gave 0.72 [0.61, 0.84]. Across all events pooled together, b was 0.34. That number says more about mixing magnitude scales and networks than about the Earth, and the page says so beside it. No sequence that week reached 30 aftershocks, so there was no Omori fit on live data; an injected synthetic sequence of 200 aftershocks with p = 1.1 came back at p = 1.08.

Polling for 45 minutes from 19:19 UTC recorded 9 new events and 7 revisions. Six magnitudes changed, by 0.19 on average, including an Alaska event that moved from 1.6 to 1.9. One event changed its preferred id from the Alaska network's to the USGS national one, and the merge logs that as a revision instead of a deletion plus a new event.



## A Test That Failed for the Right Reason

My first b-value test failed. Its synthetic catalog had a true b of 1, and the 95% bootstrap interval came out [1.015, 1.070], missing it. A 95% interval should miss about one time in twenty, and across 300 synthetic catalogs this one covered the true value 93.7% of the time. The single catalog test now uses a different seed, and a separate test requires at least 16 of 20 catalogs to cover the true value.



## Honest Limitations


  
- Mixed magnitude scales. The feed combines ml, md, mb and moment magnitudes from many networks, so pooled b-values are not physical estimates.
  
- One week is short. Aftershock fits are only possible after a sizeable mainshock, which most weeks do not have inside a region.
  
- Deletions are untested on live data. None occurred in 55 minutes of polling, so the deletion logic has only been exercised on synthetic feeds.
  
- Coarse coastlines. The 1:110 million land outlines are rough for Hawaii and Puerto Rico.


  

## What This Project Demonstrates

  Statistical seismology implemented from the papers and tested for calibration, together with the data engineering a mutable public feed needs: merging, revision tracking, id changes and deletions.



==================== PROJECT 3: Space Weather Nowcast: Solar Wind from L1 to the Aurora over Syracuse
META: Space Physics / Live Data / Oct 2026
BADGE: 9 NOAA feeds joined on time / L1 to Earth delay from the spacecraft ephemeris / Shue magnetopause, live
TAGS: JavaScript, Data Integration, Time Series Joins, Space Weather, Shue Model, Newell Coupling, d3-geo, Freshness Monitoring, node:test
REPO: "https://github.com/TanayPratapSingh/space-weather-nowcast"
9 NOAA feeds joined on time  |  run Oct 8 2026, 19:38 UTC: solar wind at 360 km/s, reaching Earth 73.5 min after it was measured 1.58 million km away  |  magnetopause at 10.9 Earth radii  |  M6.7 flare in the X-ray record  |  20 tests
The solar wind on October 8, 2026. Each dot is one minute of wind measured at L1, placed by its own speed on the way to Earth; orange means the field points south, which lets energy in. Not to scale.


## Why This Matters

My Kp forecasting project trained an LSTM on hourly solar wind history from NASA's OMNI2 dataset. Clean history is the easy part. A model like that would run in production on the live feeds, which arrive from several spacecraft, at different cadences, with gaps, revisions and switches between instruments. This dashboard builds that input side. It joins NOAA's real time feeds, propagates the measurements to Earth, turns them into the quantities that drive geomagnetic activity, and shows how fresh each input is.



## From L1 to Earth

Spacecraft near the L1 point measure the solar wind about an hour before it reaches Earth. The page joins the plasma and magnetic field feeds on time for whichever spacecraft NOAA marks active, reads that spacecraft's actual position from the hourly ephemeris, and divides its distance by the measured solar wind velocity to get a ballistic delay. Every solar wind chart marks the sample whose plasma is reaching Earth now.



## What It Computes

Dynamic pressure from density and speed; the Newell et al. (2007) coupling function, which combines speed, field strength and clock angle into a single predictor of how much energy enters the magnetosphere; and how far the edge of Earth's magnetic field sits on the Sun side (the magnetopause standoff, from the Shue et al. 1998 model), drawn live against the orbit of geosynchronous satellites at 6.6 Earth radii. It also shows GOES X-ray flux with flare classes, Kp from the 1 minute estimate alongside NOAA's 3 day forecast and the G scale, and NOAA's OVATION aurora forecast on a polar map with the night side shaded from the computed subsolar point.



## Measured on Real Data

A node run of the same code at 19:38 UTC on October 8, 2026 found the spacecraft labelled SOLAR1 active at 1.58 million km sunward. The latest joined sample showed 360 km/s and 5.7 protons per cubic centimetre, giving a dynamic pressure of 1.24 nPa, a magnetopause standoff of 10.9 Earth radii, and an arrival 73.5 minutes after measurement. Plasma covered 1,265 of the previous 1,435 minutes. The GOES record held an M6.7 flare at 15:48 UTC, and NOAA's forecast peaked at Kp 5.67 (G2) for 06:00 UTC on October 9.



## Things the Feeds Taught Me

My spec was wrong about the G scale. I had specified that Kp 4.67 counts as below G1. NOAA's own forecast file labels 4.67 as G1 and 5.67 as G2, because NOAA rounds Kp to the nearest whole number before mapping. The page follows NOAA, both rules are implemented and tested, and the method section explains the choice.

NOAA rewrites recent minutes. Between two versions of the 1 minute Kp file fetched seconds apart, recent minutes changed value. The page keeps the latest version of each minute and counts revisions, so a window's maximum can go down as well as up.

Hidden tabs. Polling pauses while a tab is hidden to save bandwidth, which meant a page opened in a background tab showed nothing until it was viewed. The first poll now always runs, and later ones wait for the tab to be visible.



## Honest Limitations


  
- Ballistic propagation is approximate. Solar wind fronts are tilted, so the real arrival can differ by several minutes.
  
- The Shue model is symmetric and ignores dipole tilt; it is an empirical fit, not a simulation.
  
- Past forecasts are not scored. The feeds carry no archive of NOAA's earlier predictions, so the page compares the current window's forecast with the live estimate rather than claiming a skill score.
  
- Aurora at the nearest grid cell. OVATION is read at one degree resolution, and cloud and light pollution are not modelled.


  

## What This Project Demonstrates

  Multi source integration with time alignment, gap handling and freshness monitoring, physical models implemented from the papers and tested against reference values, and the production input side of a forecasting model I built earlier.



==================== PROJECT 4: Replicating Dr. GRPO: Accuracy Held, the Length Claims Came Out Reversed
META: Reinforcement Learning / Reproducibility / Sep 2026
BADGE: 51.6% vs 51.2% on MATH500 / both length claims reversed / 1 seed, 100 steps
TAGS: Reinforcement Learning, GRPO, PyTorch, LoRA, vLLM, Qwen2.5, MLX, Bootstrap Intervals, Reproducibility
REPO: "https://github.com/TanayPratapSingh/drgrpo-replication"
MATH500: Dr. GRPO 51.6% vs GRPO 51.2%, paired +0.4 points [-3.4, +4.0]  |  Dr. GRPO 99 tokens longer per step [77, 123]  |  wrong answers 680 vs 545 tokens  |  1 seed, 100 steps, 500 paired eval problems  |  every number traces to runs/kaggle/



## Why This Matters

GRPO is the objective behind DeepSeek-R1-Zero, and Liu et al. 2025 argue it has two biases built in. It averages each response's loss over that response's own length, so a long wrong answer is penalised less per token than a short one. It also scales each question's advantages by the standard deviation of the group's rewards. Dr. GRPO deletes both terms. The paper reports three things: response length keeps growing under GRPO but not under Dr. GRPO, Dr. GRPO's wrong answers are substantially shorter, and accuracy does not suffer.

I rebuilt the comparison on the paper's own Figure 5 setup, at the scale a free GPU allows, to see which of the three claims survive.




## The Setup

Qwen2.5-1.5B base, the R1 template, MATH training questions, and a binary reward for a correct answer inside the answer tag. The grader is the authors' own code, vendored unmodified, and the training and eval data are their published files. Each step samples 8 responses for each of 16 questions, 128 in all, and both arms train on the same 16 questions at every step. The two run configs differ in exactly two flags: std_norm and length_norm are on for GRPO and off for Dr. GRPO.

The model is 1.5B rather than 0.5B because the 0.5B base could not produce the strict answer format on MATH, which leaves GRPO with no reward to learn from. 1.5B is also the model in the paper's figure.




## What Reproduced and What Did Not

Every comparison is paired: the same questions in training and the same 500 MATH500 problems in evaluation. Brackets are 95% bootstrap intervals.

## Half the Mechanism Shows Up

The paper's argument has two sides: GRPO should make correct answers shorter and wrong answers longer. The first side appears clearly, with GRPO's correct answers at 262 tokens against 399 for Dr. GRPO. The second does not.

Truncation does not explain the gap. 55 of 500 final responses hit the 1024 token cap in each arm, and during training the arms truncated a similar share, 8.2 and 9.2 of 128 responses per step.




## What Is Not Identical To The Paper

Every deviation applies to both arms equally, and neither term under test depends on any of them. They still bound how far the result generalises.

## Checked Before It Was Trusted


  
- The per token gradient is exactly -A/|o| under GRPO and -A/budget under Dr. GRPO, tested in both the MLX and the PyTorch version of the loss.
  
- The PyTorch and MLX losses agree to 1e-6 on identical inputs.
  
- Merged weights reproduce the LoRA model's outputs before the sampler uses them.
  
- During training, the sampler's and the learner's log probabilities for the same tokens never differed by more than 0.004 nats in a step, so the policy being sampled was the policy being trained.




## Limitations


  
- One seed. The bootstrap intervals cover variation across steps and problems, not across seeds. Two runs with identical settings drift apart after the first update, because the fp16 backward pass on a GPU is not bit reproducible. The paper used three seeds. This is the biggest gap, and it is why the result reads as "not reproduced here" rather than "refuted".
  
- Short and small. 100 LoRA steps at a 1024 token budget. The paper's effect could need longer training, full fine tuning, or room to grow past 1024 tokens.
  
- The mean hides structure. Both arms reach the same accuracy by different routes, and GRPO's length collapse between steps 55 and 80 is unexplained.




## Engineering Notes

The experiment started on an Apple M5 laptop in MLX and moved to Kaggle when the laptop became unusable during runs. Problems found along the way, each fixed in its own commit:


  
- A Metal GPU timeout, caused by macOS paging out GPU buffers under memory pressure, fixed by wiring the working set.
  
- vLLM on a T4 ran at 350 tokens per second. The cause was per request sampling seeds, not LoRA, and removing them tripled throughput.
  
- Building all the merged weights at once ran the sampler GPU out of memory. They now stream one tensor at a time.
  
- PyTorch reports bf16 as supported on a T4 by emulating it, so bf16 is keyed on compute capability instead.

  I can rebuild an RL post training result from the paper's own model, data and grader, keep the two arms paired so the comparison means something, and report a disagreement with the paper without overstating it. Code, figures and every run artifact are at github.com/TanayPratapSingh/drgrpo-replication.



==================== PROJECT 5: Tool Dependency Graph: Deriving Agent Call Order from 1,391 Tool Schemas
META: Agent Infrastructure / Static Analysis / Sep 2026
BADGE: 1,391 tools / 46 typed entities / 3,278 edges / 8 of 8 assertions passing
TAGS: TypeScript, JSON Schema, Agent Tooling, Tool Orchestration, Graph Construction, Static Analysis, Cytoscape, Bun, Data Modeling
REPO: "https://github.com/TanayPratapSingh/tool-dependency-graph"
1,391 tools across two large toolkits  |  46 typed entities  |  3,278 edges  |  1,768 of 1,770 typed required inputs have a producer  |  every edge traces to a declared output field


## Why This Matters

Agents fail on tool calls for a boring reason. The call needs an argument the agent has no way to produce. A reply tool wants a thread_id, and nobody has one memorised: it is an opaque handle that only exists because some earlier call returned it. An agent that does not know this ordering either hallucinates the handle or asks the user for something the user cannot know either.

So the useful artifact is a map of which tools have to run first, and which arguments genuinely have to come from a person. This builds that map from nothing but the tools' JSON Schemas.



## Why Name Matching Fails

The twenty line version matches input parameter names against output field names and draws an edge. It does not work, for three reasons that only appear at catalog scale.

Generic names collide. id, name, query and state appear on hundreds of unrelated tools, so name matching wires a mail client to a source control API. Every handle is resolved to a namespaced entity instead, scoped to the service that owns the tool.

A bare id means nothing. The most common shape in a real catalog is data.threads[].id. The leaf is id; the meaning lives in the parent segment. Discard the path and the single most important producer in the catalog, the thread listing, becomes invisible. Resolution runs in three tiers: the leaf name, then the nearest meaningful ancestor, then the producing tool's own object.

Almost every response embeds almost every object. A workflow run response contains a full repository, so taken literally a cancel tool "produces" a repository name. True and useless. Producers are split into primary and incidental by the head noun of the tool's object phrase, and incidental ones are suppressed whenever a primary exists. English compounds are head final, which is what makes this work:


  SlugHead nounYields
  CREATE_A_REPOSITORY_VARIABLEvariablenot a repo
  CREATE_AN_ORGANIZATION_REPOSITORYrepositorya repo
  CREATE_AN_ISSUE_COMMENTcommentnot an issue

All three are wrong under token matching, and the first two point in opposite directions despite both containing the word repository.



## Why the Graph Is Bipartite

The natural encoding is an edge from every producing tool to every consuming tool. At this scale it collapses: one entity, the repository owner, is required by hundreds of tools and produced by dozens, so that entity alone emits tens of thousands of edges and the picture says nothing.

Tools and entities are both nodes instead. A listing tool produces gmail.thread_id; gmail.thread_id is required by the reply tool. Edge count drops from producers times consumers to producers plus consumers, the hub structure becomes legible, and the two hop path is exactly the answer to "what do I run first".




## What the Numbers Say, and What They Do Not

Of 2,728 required inputs across the catalog, 1,770 resolve to a typed entity, and 1,768 of those have at least one tool that can supply them. The headline is 99.9 percent, and it would be dishonest to leave it there: that is coverage of the inputs that resolved to an entity, not of all required inputs. The honest version is that 65 percent of required inputs are typed handles and almost all of those are satisfiable. The rest are content a person writes, paging knobs, enums, and 568 handle shaped parameters the registry does not cover yet.

Those 568 are reported rather than hidden. They are how the entities for repository id, project id, runner id and invitation id were found in the first place: the unresolved bucket is the registry's own to do list.

A slug based inference fallback was built for tools with no output schema. It fired zero times. Real output schemas covered every tool that needed one, so every edge in the graph traces to a declared field rather than a guess.



## How It Is Checked

Eight hand written assertions, run with one command. All eight pass now, and every one of them started out failing. Four were real bugs that only surfaced because the assertions were written against the two dependency shapes the project exists to get right, rather than against whatever the code already did:


  
- the bare id under threads[], which hid the most important producer in the catalog
  
- cross service producers leaking into a plan, so a mail tool was told to call a source control tool to find an email address
  
- requiredness not compounding through an optional parent, so fields inside an optional attachment object were reported as required user input
  
- the head noun error above, which credited a tool that creates a variable with creating a repository

None of the four were visible from reading the code. They appeared the moment the output was compared against a case someone had written down in advance.


==================== PROJECT 6: Distributed ViT on CIFAR-10: Proving a Speedup, Then Explaining Why It Vanished
META: Distributed Training / Systems Measurement / Sep 2026
BADGE: 98% -> 57% scaling efficiency / cause isolated / 24 measured runs
TAGS: PyTorch, DDP, FSDP, NCCL, Mixed Precision, torch.compile, Vision Transformer, CUDA, Benchmarking, Apple MPS
REPO: "https://github.com/TanayPratapSingh/distributed-vit-cifar10"
2x Tesla T4, NCCL  |  DDP in fp32: 1.96x at 98% efficiency  |  identical config in fp16: 1.15x at 57%  |  cause isolated to a 4 vCPU host  |  24 measured runs across 3 hardware groups

          

## Why This Matters

          
            Almost every distributed training result you read is unfalsifiable. A repository reports a 1.9x speedup on two GPUs and there is no way to tell whether the two rank job computed the same gradient as the one rank job, whether the baseline was tuned as carefully as the treatment, or whether the number came from a machine doing something else at the time. A speedup you cannot verify is only a claim. This project was built so that every claim it makes is checkable, and its main finding is a regression in its own scaling.
          


          

## What Gets Measured, and Against What

          
            Three hardware groups: an Apple M5 laptop with one GPU, multi process gloo over that laptop's 10 CPU cores, and 2x Tesla T4 on Kaggle with NCCL. Speedup is only ever computed inside one group, because a ratio between a T4 and an M5 is arithmetic, not a measurement. A rank scaling baseline must differ from its run in exactly one property: the rank count. Precision, compilation, gradient accumulation, dataloader worker count, epoch count and dataset fraction all have to match, and the reporting layer enforces that rather than trusting the author. That constraint was added after the dashboard was caught dividing a real data run by a synthetic data baseline, which silently reported 1.11x where the matched comparison is 1.15x.
          


          

## Model and Data

          
            A vision transformer written out rather than imported, 1,806,538 parameters, patch size 4 on 32x32 inputs giving 64 tokens plus a class token. It is small on purpose, because the model must not be the bottleneck in a throughput measurement, and at this size the gradient payload for each all reduce is about 7 MB. CIFAR-10, 50,000 train and 10,000 test, 30 epochs, no pretraining.
          

          
            The canonical dataset host was unreachable from the development network, failing with an SSL EOF before any payload arrived. The fallback deliberately does not rebuild the original pickle layout, because those files carry published md5 sums a reconstruction cannot match, and the only way to make that path appear to work would be to disable torchvision's integrity checking. Silencing a checksum to make a download look successful is how results stop being trustworthy. The mirror writes its own format instead, and every run artifact records which source it used.

            DDP averages gradients across ranks, so two ranks each holding batch B must produce the same gradient as one process holding batch 2B. ## The Prediction That Was Wrong

          
            The third prediction said DDP would land near 1.8x rather than 2x, reasoning that a small model makes the all reduce expensive relative to compute. That is backwards. A small model means small gradient tensors, about 7 MB, which DDP overlaps with the backward pass almost entirely. In fp32 it scales at 1.96x, 98% efficiency.
          

          
            The same DDP configuration in fp16 scales at 1.15x, 57% efficiency. Hardware, model and communication volume are identical, and the only thing that changed is that each GPU now computes roughly twice as fast. Optimising one layer moved the bottleneck rather than shortening the job, and scaling efficiency turned out not to be a property of the cluster at all.
          


          

## Isolating the Cause

          
            Two suspects: the NCCL all reduce, and the input pipeline. Raising the dataloader worker count and watching what happens would produce a correlation, not a cause. Instead a synthetic input mode serves pre normalised tensors from a small in memory pool, removing decode, augmentation and worker processes entirely, so two ranks against one rank under it is compute plus communication with nothing else in the measurement.
          

          
            Input path1 rank2 ranksSpeedupEfficiency

            The collective is innocent. With no dataloader the same configuration scales at 1.92x, 96% efficiency. With real data, throughput never passes about 4,073 img/s no matter how many GPUs or workers are thrown at it. The artifacts record cpu_cores: 4. One T4 in fp16 already consumes 3,956 img/s of synthetic input, so 4 vCPUs cannot feed even one GPU comfortably, let alone two. The second T4 is not slow, it is unfed.
          

          
            Raising workers from 2 to 8 per rank made it worse, 3,996 against 4,073, because 16 worker processes on 4 cores buy context switches and nothing else. The synthetic runs also index a small pool, so their 96% is an upper bound on what fixing the input path could achieve, not a promise.

## Precision Advice Does Not Survive a Backend Change

          
            On the T4, enabling mixed precision is a 2.06x win. On Apple silicon the identical flag is a regression: 726 img/s against 1,061 in fp32, a 32% slowdown, because eager mode pays for a cast around every operator and the hardware is already efficient at fp32. Adding torch.compile to that same fp16 configuration reaches 2,361 img/s, 2.23x the fp32 baseline, once the casts are fused into the graph. Wall clock for the full 30 epoch run falls from 24 minutes to 11.
          

          
            A related trap is that on a T4, torch.cuda.is_bf16_supported() returns True. The card is sm_75 and has no hardware bf16, so that True reflects emulation. Trusting it selected an emulated path for every mixed precision run, and torch inductor quietly logged that the card does not support bfloat16 natively while the benchmark carried on reporting the result as mixed precision. Precision is now selected from compute capability, and every artifact records the dtype that was actually used.
          


          

## Accuracy as the Control

          
            Across all seven T4 configurations, top-1 spans 79.41% to 80.70%, and the three Apple silicon runs land within 0.16 points of each other. That spread is the control. These are throughput changes, so accuracy should barely move. If mixed precision or compilation had shifted it materially, the correct output would have been a bug report rather than a results table.
          


          
            
            Figure 3. Test accuracy by epoch. The curves overlay because precision and compilation change throughput, not learning. The reporting layer excludes short and synthetic runs from this view.
          

          

## Nine Bugs, Kept On Purpose

          
            The defect log is the most reusable output of the build, so it ships in the repository rather than being tidied away. Four of the nine came from an API answering a slightly different question than the one being asked: is_bf16_supported counting emulation, torchvision's md5 check rejecting a legitimate mirror, MPS reporting instantaneous memory where a peak was wanted, and sys.argv[0] producing a command that could not reproduce its own run. One was a hang rather than a crash. The default TCP rendezvous is blocked on some hosts and the job waits, which reads exactly like slow training and costs hours before anyone suspects the launcher. Three were wrong numbers on the dashboard, all found by pointing a screen recorder at a page nobody had read closely.
          

          
            That last category is why the honesty rule is now enforced rather than promised. A gate extracts every number carrying a measurement unit from the documentation and fails if it does not round, at the precision it was written with, to an artifact value or to a ratio between two artifact values on the same hardware. It found five unsupported claims the first time it ran.
          


          
            

## Operational Reading

            
              The same cluster, model and communication volume delivered 98% efficiency in fp32 (the 1.96x) and 57% in fp16, and the difference had nothing to do with the distributed layer. Anyone tuning NCCL in response to that drop would have spent a week in the wrong subsystem. Scaling efficiency is a property of the ratio between accelerator speed and host speed, and optimising the accelerator is what breaks it. The measurement that settles it took six short runs and one flag.

## Why This Matters

          In time domain astronomy the telescope produces far more data than any human can look at, and the overwhelming majority of it is noise. A survey astronomer or alert broker operator needs high purity transient candidates surfaced quickly, and needs to trust that the nightly numbers behind them are correct. Those are two jobs: a fast, accurate model at the front, and a tested, governed data layer behind it. I built ZTF Transient Pipeline to do both in one system. It also maps onto the three roles I am applying for: ML engineer, data engineer, and analytics engineer.


          

## The Sequel to ShopFloor

          I designed this project to close the three gaps I listed as limitations in ShopFloor AI, and to do it on production shaped infrastructure. Simulated Kafka becomes real Avro alert data flowing over a real Kafka broker. A synthetic benchmark dataset becomes a public survey stream. The single node app gains a real warehouse, a dbt transformation layer, and drift monitoring.


          

## The Data

          The Zwicky Transient Facility (ZTF) streams over a million optical alerts per night as Avro packets over Kafka. Each packet embeds three small image cutouts (science, template, and difference) plus a table of measured features. The pipeline downloads a night of real archived alerts and replays them through its own Dockerized Kafka broker. The payloads are genuine ZTF data; only the timing is replayed. The README says so plainly. Replaying the archive puts real data through a real broker without needing broker whitelisting on the critical path.


          

## Streaming ML Plane

          fastavro deserializes the alerts, and Astropy handles the astronomical coordinate and time conventions. A multimodal classifier in TensorFlow and Keras scores each alert: a convolutional branch reads the three image cutouts, a tabular branch reads the measured features, and the two are fused to predict whether an alert is a real transient or an artifact, then a coarse class. Rather than invent an accuracy target, the model is framed against BTSbot, a published survey broker classifier that scores detections from the same image plus feature inputs. A FastAPI service exposes the scorer, and a streaming consumer writes predictions and alert metadata into the warehouse.


          

## Analytics Engineering Plane

          This half is the SQL and analytics engineering work. A dbt project transforms the raw landed alerts through three layers: staging models that clean and type the raw stream, intermediate models that assemble per object lightcurves using window functions, and mart models including an incremental daily alert summary and a model monitoring rollup. The project ships with 21 data quality tests, source freshness checks, and generated lineage docs. It defaults to DuckDB so anyone can run it with zero cloud setup, and the same models port to BigQuery and Snowflake with only a profile change.


          

## Orchestration and Monitoring

          An Apache Airflow DAG runs the full nightly batch end to end: download, deserialize, load, transform, and monitor. A Population Stability Index drift monitor watches the prediction distribution over time, so a shift in what the model is seeing surfaces as a number rather than a surprise. Continuous integration through GitHub Actions runs the test suite and a dbt build on every push, and a Codespaces devcontainer lets the whole thing spin up in the browser.


          

## Proven on Real Data

          I ran the pipeline against a real night of the survey: 27,378 Avro alert packets extracted from July 20, 2026. Of those, 500 alerts were loaded, scored, and rebuilt through the warehouse. A full dbt build returned 8 models and 21 tests with 32 checks passing and zero errors, on real data rather than a seed sample. The repository is public at github.com/TanayPratapSingh/ztf-transient-pipeline.


          

## Honest Limitations

          
            
- Replay, not live consumption. Nightly archive replay uses real data, but live streaming from the survey broker needs an IP whitelist, so it is kept as an optional upgrade rather than a dependency.
            
- Coarse labels. The classifier demonstrates the pipeline, not a science grade taxonomy. It is a systems project first.
            
- Trial scale compute. Everything runs single node under Docker Compose, not at production survey volume.
            
- Validation against broker labels. There is no spectroscopic confirmation, and the reference labels are themselves model outputs, so the benchmark is relative rather than ground truth.
          

          
            

## What This Project Demonstrates

            One repository covers all three roles. For ML engineering there is a multimodal image plus tabular classifier benchmarked against BTSbot; for data engineering, a real Avro over Kafka ingestion pipeline that Airflow orchestrates nightly; for analytics engineering, a dbt transformation layer with tests, freshness checks, lineage, and warehouse portability.

## Why This Matters

Reading a paper tells you what the authors claim. Rebuilding it tells you whether the claim survives contact with a different machine, a different implementation and a fresh set of defaults. I rebuilt the central experiment from BEIR (Thakur et al., NeurIPS 2021 Datasets and Benchmarks) from scratch: the claim that dense retrievers trained on MS MARCO lose to a plain bag of words baseline once you move them to a domain they were not trained on.

The useful part of a replication is the one cell that disagrees, because chasing it is the only way to learn something the paper did not tell you.




## What Reproduced

I used two scientific datasets from the benchmark, chosen because they are the smallest and therefore fit on a laptop: SciFact (5,183 documents, 300 queries) and NFCorpus (3,633 documents, 323 queries). Both counts match the paper exactly. The metric is nDCG@10, scored with pytrec_eval, the same trec_eval bindings the authors report with.

## The Cell That Disagreed

DPR on SciFact came in at 0.260 against a published 0.318. Not a rounding difference. TAS-B had already reproduced exactly on both datasets, so the loader, the metrics and the scoring were not at fault, which left something specific to how DPR sees a document.

The cause is a default. The sentence-transformers port of the DPR context encoder ships with max_seq_length = 100, so every abstract was cut off after roughly its first paragraph. No error, no warning, no sign of it in the output. The tell was that searching with only the title scored 0.261 against title plus full text at 0.260. That only makes sense if the body was being discarded.

META: Agent Orchestration / Human in the Loop / Sep 2026

212 tests / 11 behavioural scenarios / zero dependencies / unanswered page -> safer substitute / CI green on Python 3.11 to 3.13



## Why This Matters

Most human in the loop is a modal dialog that blocks forever. The agent reaches something risky, calls confirm(), and waits. It does not say who is being asked, it does not say how long they have, and it has no answer at all for the case that actually happens at 3am, which is that nobody replies. An agent parked on an unanswered prompt is worse than one that never asked, because the incident is still burning and now nothing is watching it. handoff treats escalation as a routing problem with tiers, skills, load, deadlines and a written down behaviour for silence, and builds the rest of the system around that.




## The Sequel to comms-agent

comms-agent put a human in the loop gate inside an agent graph: flag the low confidence items, let a reviewer correct them, then report. That answers what happens when the reviewer shows up. handoff covers what happens when they do not, which is the case that breaks these systems in production.




## Escalation as Policy, Not a Callback

The policy is a table keyed by risk, held as data in config/policy.yaml: which tiers may approve, in what order, how many seconds the first tier gets, how many signatures are required, and what happens on expiry. Because it is data, somebody who does not read Python can review it in a pull request. Four classes of mistake are caught at load time rather than during an incident: a rule that requires approval without stating an expiry behaviour, a quorum larger than its own ladder, a ladder tier that no responder stands on, and a declared fallback that is missing, self referential, or not actually safer.




## When Nobody Answers

An irreversible failover_database is proposed. The page goes to the engineer on call who holds the infrastructure skill, with 180 seconds to answer. Nobody answers. The system neither fails over nor sits still. It runs enable_read_only instead, the substitute the failover tool itself declares. Writes are rejected and checkout degrades, but no transaction in flight is lost and a human can reverse it on arrival. The journal records that it happened because nobody answered, which is a different fact from a human deciding it was a good idea.




## Disagreement Is a Second Trigger

Risk is not the only reason to involve a person. When the log analyst sees a high error rate and the metrics analyst sees healthy latency, both confidently, the hypothesis is marked contested rather than averaged into a clean answer the system does not actually have. Any action that addresses a contested hypothesis has its effective risk raised one level, so a low risk service restart that would normally run unattended stops and asks. Uncertainty about the diagnosis and danger in the fix are different problems with the same remedy, and one mechanism means nobody has to remember to wire up a second check.




## What It Refuses To Do

The expiry behaviours are deny, safe_fallback, escalate and hold. There is deliberately no allow. Approving an action because nobody looked at it in time is not approval; it is the absence of a decision written down as though it were one. A ladder whose terminal state can be "ran it anyway" is a delay mechanism wearing the costume of a control. A test asserts that the enum member does not exist, so adding it means deleting a test whose docstring explains why it should not.




## Honest Limitations



- The cluster is simulated. It is a dataclass. Nothing in the project has talked to Kubernetes, a database, or a real pager.

- Rules, not models. The five workers are deterministic with hand written thresholds, and no LLM is called anywhere. Whether the escalation layer holds up when the workers are nondeterministic is the open question this project does not answer.

- No scheduler. The caller drives the deadline tick, which is what makes every deadline testable at its precise boundary. It also means a deployment needs something that calls it on a timer, and that part is not written here.

- No notification channel. The journal exposes a subscribe hook where a pager would attach. Nothing attaches to it.

- Static roster. Seven people in a YAML file, with no rotation schedule, timezones, or handover.





## What This Project Demonstrates

In handoff the supervision is the product rather than a wrapper around it. A supervisor is the only component permitted to execute. Workers are handed a registry filtered to read only tools, so they cannot reach a mutating one by name. The escalation layer has tiers, skills, load balancing, quorum, deadlines and a declared behaviour for silence. There are no dependencies, so the whole suite runs on a bare interpreter in under a tenth of a second. During the build the suite caught two design flaws, one of which was a safety path that could never actually run.

==================== PROJECT 14: Project Mark: Designing Deterministic Analytics Traps to Stress Test Frontier Models
META: AI Evaluation / Analytics Red Teaming / Jul 2026
BADGE: 4 verified statistical traps / frontier-model evaluation
TAGS: Python, Pandas, NumPy, SciPy, Statistical Inference, Causal Reasoning, Experiment Design, LLM Evaluation, Data Cleaning, Reproducibility
REPO: ""
5 datasets profiled  |  4 trap families built and verified  |  deterministic golden solutions reproduced to the digit  |  CC licensed multi file corpora  |  frontier models solved the clean traps

          

## What The Project Was

          
            The brief was unusually specific. Every submission had to be a product analytics question of the kind a technology company actually faces, analyzing how users behave inside a digital product to drive a product, growth, or monetization decision. Each had to resolve to a single deterministic recommendation that ten domain experts would independently agree on, be reconstructible entirely from the shipped files, and be hard enough that a panel of frontier models would fail it. A valid stump had a concrete bar. Across eight model responses, at least two of the first four and one of the second four had to land on a meaningfully different answer. Difficulty had to come from methodology and reasoning, never from vague wording or a trick definition.
          


          

## The Real Constraint: Fairness Plus Difficulty At The Same Time

          
            A good task has to be fair and hard at once. Fair means the correcting fact lives somewhere in the corpus, every file opens with standard tooling, and all defensible cleanings converge on the same answer. Hard means a strong analyst, or a strong model, still gets it wrong on the first pass. The input files also had to be real and properly licensed (public domain or Creative Commons only, verified per dataset) and never model generated, with six or more files across a variety of formats and several of them load bearing. Satisfying every one of those at once, on real data, is most of the work.
          


          

## Traps I Built And Verified

          
            Every trap below was implemented against real data and checked with code so the intended answer reproduced exactly before anything shipped. Each one pairs a headline number that is real, easy to compute, and misleading with a correcting analysis that a rushed solver skips.
          

          
            
- Composition shift (Simpson's paradox). A blended retention or conversion metric that declines quarter over quarter while every underlying segment is flat or improving, because the mix of segments moved. The naive read (the product is getting worse) is refuted by a segmentation the solver has to discover and join across files on a mismatched key.
            
- Outlier artifact in an A/B revenue test. On a real experiment dataset, one arm's revenue looked competitive, but 123 users (0.06 percent of the group) each paid a near identical anomalous amount and accounted for 89.4 percent of that arm's revenue, while the other arm had none. The correct call requires recognizing the cluster as non genuine, handling the zero inflated heavy tailed distribution properly (decompose conversion times value, use robust tests), and flipping the decision the raw averages imply.
            
- Confounded and circular metrics. A composite health score presented as independent corroboration that actually embeds the very metric under investigation, so citing it double counts one signal. The same family covers correlation dressed up as causation on observational data.
            
- Mismatched population merges. A distractor file with similar looking columns that covers a different population entirely (different platform, window, or cohort), tempting a solver to merge it in and report a figure that does not apply to the group in question.
          

          

## The Final Task: An Engagement Feature Decision On Real Learning Platform Data

          
            The most fully developed task used the Open University Learning Analytics Dataset (real virtual learning environment click logs, registrations, and outcomes for tens of thousands of students, released under CC BY). The business question was which one engagement initiative to fund to raise course pass rates: a richer per session experience, or a nudge to return on more days. A shipped internal pre read recommended the per session option, backed by a real and reproducible correlation (total clicks versus passing at r = 0.56, with pass rate climbing from 0.3 percent to 91.9 percent across activity quintiles).
          

          
            That correlation is the trap. Total activity confounds two distinct levers: how many days a student returns, and how much they do per session. Decompose clicks into active days times clicks per active day, regress both against passing, and the entire association lives in return frequency (standardized effect around 0.24, and about 0.34 with all students included). Per session intensity collapses to essentially zero once days present is controlled. The result held within every module and whether or not withdrawn students were included, so the deterministic answer is to fund return frequency, not intensity. I built two corroborating decoy artifacts pointing at the wrong lever and verified that every figure reproduced from the raw files. The task cleared the program's automated construction and determinism checks.
          


          

## Why This Is A Happy Failure

          
            It did not stump the models. In repeated live rollouts, strong frontier models independently rebuilt the analysis from the raw files, ran the frequency versus intensity decomposition, ignored the decoy pre reads, and reached the correct answer, often quoting the exact adjusted numbers. Hardening the framing and adding more authoritative decoys did not change the outcome. The reason is structural. The move that cracks the task, decompose a composite metric and test the parts, is a reflexive step for a capable analyst, so a frontier model does it whether or not the prompt signposts it.
          

          
            Stumping a frontier model on a clean, fair analytics problem requires a trap that sits outside a strong reasoner's default repertoire, which is a far higher bar than "a smart person would need to be careful here." I watched capable models reject a plausible but confounded headline artifact and reconstruct the correct causal story from first principles. That is a calibrated data point about where these systems are now strong, and it changed how I think about designing evaluations for them.
          


          
            

## What This Project Demonstrates

            
              I built adversarial, deterministic traps (Simpson's paradox, outlier and confounding artifacts, correlation versus causation, population mismatches) on real, licensed, multi file data and verified each one reproducibly. Trying, and failing, to beat frontier models fairly is what gave me a calibrated read on their capability. The less visible work was disciplined data provenance and licensing, golden solutions checked to the digit before shipping, and reporting an honest negative result.

            Few calls in motorsport carry more weight than pit stop timing. A miscall on lap selection can cost a team between two and five constructor championship positions over a season, which means millions of dollars in lost prize money and sponsorship value. Race engineers make these calls in the moment, with limited time, from experience and real time telemetry. The premise of this project was that if a model can predict the optimal lap accurately enough, it becomes a live sanity check that the human strategist either validates or knowingly overrides, instead of a guess they make alone.
          


          

## Stakeholders and Value

          
            
- Race engineers get a predicted first pit lap on race day, a baseline they can use to justify or override their intuition.
            
- Strategy directors get patterns across decades of races for pre season planning, such as circuit and race length outweighing driver identity.
            
- Broadcast analysts and fantasy F1 platforms get a predicted pit lap, and the features that drove it, to explain to viewers.
          

          

## Data and Cleaning

          
            The source is the Formula 1 World Championship dataset on Kaggle (1950 to 2020), with 250,000+ records across thirteen interconnected tables (races, results, pit stops, drivers, constructors, lap times, qualifying, status codes, circuits, and more). I added a custom track_features table with tire degradation level and pit lane time loss per circuit, because these physical factors drive strategy and the raw schedule data does not capture them well. The data was filtered to post 2000 races to focus on the modern tire era, since pre 2000 strategy was driven by fuel weight rather than tire compounds. The final modeling dataset is 14,000+ driver race rows with 45 engineered features.
          

          
            Cleaning removed invalid pit lap records (below lap 1 or above lap 40 are data entry errors), stripped drivers with more than two pit stops per race (these signal damage or weather chaos rather than normal strategy), and dropped early DNFs so the training set reflects strategic behavior rather than mechanical failures.
          


          

## Recovering Missing Data

          
            Pit records before 2012 were sparse. Dropping every row with a missing pit lap would have shrunk the dataset from 10,000 rows to 3,000. I trained a dedicated Random Forest imputer that recovered roughly 70% of missing first pit laps using six predictors that are reliably present even in older races: driver ID, constructor ID, race year, starting grid position, total race laps, and circuit ID. Imputation MAE was about six laps on a held out validation set, which is tolerable given pit windows typically span ten to fifteen laps.

I left out neural networks and SVMs on purpose, because they are computationally heavier and consistently underperform tree ensembles on tabular data with this feature mix.

            SHAP analysis on the Random Forest model shows that race structure features dominate the prediction. The top five contributors are total laps, planned pit stop count, year (proxying for regulation changes), round, and starting grid position. ## Practical Implication

            
              Pit timing is more a property of the physical system (circuit, race length, planned stops) than of the person behind the wheel. For engineers, that means adapting strategy to circuit and race length first, team history second, driver style third.
            

          

          

## Deployment

          
            The final Random Forest model was serialized and packaged into a Streamlit web application (team_omega_rf_app.py). Race engineers input live race context (circuit, grid position, planned stops, weather) and the app returns a predicted first pit stop lap in real time, alongside the SHAP feature importances that drove the prediction. Serialized model artifacts (f1_random_forest_model.pkl, model_features.pkl) live in the project repository.
          


          

## Honest Limitations

          
            
- No live race signals. Safety car deployments, sudden weather changes, and real time tire telemetry are absent. These drive real pit decisions, so there is a genuine information gap between the static model and live race conditions.
            
- First stop only. The model predicts only the first pit lap, not full multi stop strategies. Later stops depend on the first, and the current approach does not capture that dependency.
            
- No competitor model. Real strategy reacts to opponents (undercuts, overcuts). The model encodes neither opponent positions nor gap sizes.
            
- Regulation drift. F1 rules change often. Patterns from early 2000s races may not apply directly to current regulations, which slightly dilutes accuracy when predicting contemporary strategy.

==================== PROJECT 21: Travel Itinerary Management System
META: Database Engineering / Jan 2025 to May 2025
BADGE: 12-entity normalized schema / full itinerary in one call
TAGS: SQL, Data Modeling, Stored Procedures, Triggers, User Defined Functions, ERD Design, 3NF
REPO: ""
12 normalized entities  |  3 stored procedures  |  2 triggers  |  1 user defined function  |  Single procedure call generates full itinerary

          

## Why This Matters

          
            An itinerary database carries rules that have to hold on every access path: an activity cannot have negative cost, a hotel must belong to a real destination, an itinerary cost should always equal the sum of its components. Put those rules in application code and each new feature or platform reintroduces them, badly. This project puts them in the database itself, so any client (web, mobile, batch import, ad hoc SQL) gets the same guarantees automatically.
          


          

## Stakeholders

          
            
- Travelers creating a trip get one call that returns a complete itinerary, with the duration and cost checks already run.
            
- Application developers stop writing defensive code in three languages to enforce rules the database already enforces.
            
- Data analysts querying the database directly get consistent data, because the triggers and foreign keys also apply to rows written through direct SQL.
          

          

## Entity Relationship Design

          
            The schema has twelve entities in third normal form with full referential integrity. The core entity is itinerary, which links to destinations, activities, accommodations, transportation, seasonal information, and tags through explicit foreign keys.
          


          
            
            Figure 1. Logical ERD with all 12 tables, primary keys, foreign keys, and cardinality relationships
          

          

## Stored Procedures

          
            Three procedures cover the operations a travel app actually performs:
          

          
            
- sp_add_full_itinerary_single: Inserts a complete itinerary (activity, transport, accommodation, season info, tag) in a single atomic call. It replaces five separate inserts plus consistency checks at the application layer.
            
- sp_get_full_itinerary: Returns every linked detail of an itinerary by ID, with the joins done inside the database.
            
- sp_get_itineraries_for_destination: Lists all itineraries available under a selected destination, the most common browse query.
          

          

## Triggers for Data Integrity

          
            
- trg_check_activity_duration: Rejects any activity insert or update where duration is zero or negative. That catches UI bugs and data import errors that would otherwise silently corrupt the cost calculations downstream.
            
- trg_check_activity_cost: Rejects negative cost entries, which usually indicate a typo or unit conversion error rather than a genuine refund.
          

          

## Function for Reusable Logic

          
            
- ufn_estimate_total_activity_time: Returns the total time a traveler will spend on all activities in a given itinerary. Views, filters, and ranking interfaces call it, so itineraries can be sorted or filtered by total activity duration without each of them redoing the math.
          

          

## User Story Worked Through End to End

          
            "As a traveler, I want to create a trip by selecting options, so I can generate a full itinerary."
          

          
            The client passes destination, activity, transport, accommodation, season, and tag to sp_add_full_itinerary_single. The procedure inserts each child record, links them through the itinerary table, fires the duration and cost triggers, and returns the new itinerary_id. The client makes one round trip, and the database validates the whole insert and applies it atomically.
          


          
            

## Design Philosophy

            
              With the business rules at the data layer, the application code gets simpler and integrity holds on every read and write path. When the database itself rejects a zero duration or a negative cost, no client has to write defensive code in its own language to catch it.
            

          

==================== PROJECT 22: Digit Recognition Neural Network from Scratch
META: Deep Learning / Jan 2024 to May 2024
BADGE: 94% MNIST accuracy / built from scratch, no frameworks
TAGS: Python, NumPy, Neural Networks, Backpropagation, From Scratch
REPO: ""
94% test accuracy on MNIST  |  No ML frameworks  |  Manual forward and backward passes

          

## Why Build from Scratch

          
            Frameworks hide the parts of a neural network that are most useful to understand: the matrix shapes flowing forward, the gradient math flowing backward, and the way optimization changes the weights. Building all three by hand once gives you a working mental model of what the framework is doing underneath. When a production model later silently fails, you reason about gradient flow rather than swapping layers and hoping.
          


          

## Implementation

          
            Forward propagation is explicit weighted sums and activation functions: sigmoid in the hidden layers in the first iteration, then ReLU once vanishing gradients became visible, and softmax at the output for the ten class classification. Backpropagation computes gradients with the chain rule, layer by layer, using an explicit derivative formula for each activation function. Training runs in a mini batch gradient descent loop with tunable learning rate, batch size, and network depth.
          


          

## Tuning

          
            Hyperparameter tuning was iterative and manual, which was the point. With the learning rate too high the loss bounced, and with it too low, training stalled. A network that was too shallow could not capture digit structure, and in one that was too deep without proper initialization the gradients vanished. Working through these failures by hand is how you learn what each knob controls.
          


          

## Result

          
            Final accuracy was 94% on the held out MNIST test set. That is not state of the art; the goal was understanding rather than benchmark chasing. The exercise made it intuitive why deeper networks, non linear activations, and proper initialization matter.
          


==================== PROJECT 23: Real Time Big Data Inflow: Communication and Computation Delay Analysis
META: Research / Jan 2024 to Dec 2024
BADGE: 40 to 60% latency reduction / 6-dimension comparison
TAGS: IoT, Edge Computing, Fog Computing, Cloud Computing, Stream Architecture
REPO: ""
40 to 60% latency reduction potential  |  12+ primary sources reviewed  |  Comparative analysis across six dimensions

          

## Argument

          
            The implicit default in most enterprise architectures is to send everything to the cloud. For real time systems, that default is wrong. The hard design work is deciding which computations belong near the sensor (where latency is cheap but durability is fragile and storage is limited) and which belong in the data center (where storage is durable and compute is elastic but round trips cost real time).
          


          

## Approach

          
            The paper reviews twelve primary sources on stream processing, edge deployment patterns, and latency optimization in distributed systems. Each source is summarized for its proposed architecture and headline findings. From the literature, I propose a tiered hybrid architecture that pushes time critical computation toward the edge and keeps cloud tiers for durability, batch analytics, and global state.
          


          

## Comparative Analysis

          
            The paper compares cloud only and tiered architectures across six dimensions: scalability, reliability, bandwidth usage, privacy and security, cost effectiveness, and end to end latency. The tiered architecture wins on latency (40 to 60% reduction for appropriately partitioned workloads), bandwidth (less raw data crosses the WAN), and privacy (sensitive data can be processed locally). It pays a small price in operational complexity and consistency guarantees.
